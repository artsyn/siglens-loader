# siglens-loader

Скрипты, которые поднимают SigLens на своей машине и загружают в него лог из файла так, чтобы по нему можно было нормально искать.

Проверено на SigLens 1.0.57.

## Зачем

Нужно было разобрать лог HTTP-запросов к почтовому серверу: 50 тысяч строк в xlsx. В таблице такое искать неудобно, Splunk платный и недоступен, поэтому взят SigLens. Он открытый, запускается одним контейнером и понимает запросы в синтаксисе Splunk.

Загрузка в лоб дала плохой результат. Событие в SigLens выглядело так:

```json
{
  "event": {
    "ClientIp": "203.0.113.10",
    "Status": "401",
    "TimeStamp": "2025-08-20 09:58:09"
  },
  "host": "mail.example.com",
  "index": "mail_logs",
  "sourcetype": "mail:log",
  "time": 1755683889,
  "timestamp": 1791884205348
}
```

Поля спрятаны внутрь `event`, код ответа стал строкой, а `timestamp` показывает момент загрузки вместо момента запроса.

После этих скриптов то же событие выглядит так:

```json
{
  "ClientIp": "203.0.113.10",
  "Status": 401,
  "TimeStamp": "2025-08-20 09:58:09",
  "index": "mail_logs",
  "timestamp": 1755683889000
}
```

## Что было не так и как решено

| Проблема | Решение |
|---|---|
| SigLens не принимает xlsx | `xlsx_to_csv.py` переводит xlsx в CSV |
| При отправке в формате Splunk HEC все поля попадают внутрь `event`, искать приходится по `event.Status` | Поля отправляются в корне события |
| Время события заменяется временем загрузки, поле `time` SigLens игнорирует | Время кладётся в поле `timestamp` в миллисекундах, SigLens берёт его оттуда |
| Из CSV все значения приходят строками, сравнение `Status>=500` не работает | Числовые колонки отправляются числами |
| Логин и пароль лежат в заголовке `Authorization` в base64, по ним нельзя ни искать, ни группировать | Парсер раскодирует их в колонки `AuthUser` и `AuthPass` |
| Один и тот же логин записан как `name`, `DOMAIN\name` и `name@domain` | Логин приводится к одному виду |
| Повторный запуск отправки удваивает данные | Отправщик проверяет индекс до отправки и сверяет количество после |
| Контейнер SigLens работает под uid 1000 и не может писать в новый том | `siglens_up.sh` выставляет владельца тома перед запуском |

## Запуск

Нужны Docker, Python 3 и библиотека openpyxl.

```bash
./siglens_up.sh reset
python3 xlsx_to_csv.py mail_log.xlsx
python3 send_to_siglens.py mail_log.csv
```

`reset` удаляет старые данные и поднимает SigLens с нуля. Без аргумента скрипт просто запускает контейнер и данные сохраняет. `down` останавливает контейнер, данные остаются в томе.

Отправщик в конце пишет, сколько событий лежит в индексе. Число должно совпасть с числом строк в CSV.

После этого интерфейс открыт на http://localhost:5122. В нём нужно выбрать индекс и диапазон времени, в который попадает лог.

## Лог DNS и Cisco FirePower

Второй формат это текстовая выгрузка, где вперемешку лежат строки с DNS-сервера Windows и с Cisco FirePower (eStreamer). Поля записаны как `ключ=значение` через табуляцию, у DNS перед ними ещё syslog-заголовок. openpyxl для него не нужен.

```bash
./siglens_up.sh
python3 kv_to_csv.py logs.txt
python3 send_to_siglens.py logs.csv --index caldera --time-column EventTime --utc \
    --int-columns SrcPort,DstPort,BytesSent,BytesReceived,PacketsSent,PacketsReceived
```

Парсер в конце сам печатает нужную команду отправки.

Что делает `kv_to_csv.py`:

- Сохраняет все исходные поля, но убирает из имён пробелы и точки: `Question Name` становится `QuestionName`, `flowStatistics.responderPort` становится `ResponderPort`.
- Добавляет общие колонки `EventTime`, `SourceType`, `SrcIp`, `SrcPort`, `DstIp`, `DstPort`, `Protocol`, `Domain`. По ним ищется сразу в обоих источниках, например `SrcIp="10.208.24.74"` вернёт и DNS-запросы, и соединения.
- `Domain` у DNS это запрошенное имя, у FirePower хост из `ClientAppURL`, если FirePower его определил.
- Поле FirePower `timestamp` служебное для SigLens, поэтому оно переименовано в `OrigTimestamp`. Номер протокола лежит в `OrigProtocol`, а в `Protocol` записано TCP или UDP.

Время события:

- У DNS берётся из полей `Date` и `Time`. Это время самого DNS-сервера, а не syslog-заголовка: заголовок пишется при пересылке и идёт не по порядку.
- У FirePower берётся начало соединения `FirstPacketTimestamp`. Если его нет, то `timestamp` записи.
- Всё переводится в UTC, поэтому отправлять нужно с `--utc`. В каком поясе записано местное время в логе, задаёт ключ `--tz`, по умолчанию `+03:00`. Если пояс указан неверно, DNS и соединения разъедутся на несколько часов. Чтобы это поймать, парсер сверяет время записи FirePower с его же `CurrentTime` и предупреждает, если они не совпадают.

Примеры запросов:

```
Domain=*syncthing*
DstPort=22067
SrcIp="10.208.24.74" | stats count by SourceType
BytesReceived>1000 | stats sum(BytesReceived) by DstIp
```

## Настройки

`siglens_up.sh` читает переменные окружения:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `SIGLENS_IMAGE` | `siglens/siglens:1.0.57` | образ |
| `SIGLENS_NAME` | `siglens` | имя контейнера |
| `SIGLENS_VOLUME` | `siglens-data` | том с данными |
| `SIGLENS_BIND` | `127.0.0.1` | адрес, на котором открыты порты |
| `SIGLENS_INGEST_PORT` | `8081` | порт приёма |
| `SIGLENS_UI_PORT` | `5122` | порт интерфейса и поиска |

Основные ключи `send_to_siglens.py`:

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `--index` | `mail_logs` | индекс в SigLens |
| `--time-column` | `TimeStamp` | колонка со временем события |
| `--time-format` | `%Y-%m-%d %H:%M:%S` | формат времени, как в `datetime.strptime` |
| `--int-columns` | `Status,ClientPort,FrontendPort` | колонки, которые отправлять числами |
| `--utc` | выключен | считать время в логе как UTC, иначе как местное время машины |
| `--force` | выключен | отправлять, даже если в индексе уже есть события за этот период |

## Особенности SigLens, о которые легко споткнуться

- Готовые диапазоны времени в интерфейсе заканчиваются на 90 днях. Для старого лога диапазон задаётся ниже в том же списке, в блоке Custom Search.
- Срок хранения нельзя поставить больше 720 часов. Большее значение в `server.yaml` молча сбрасывается на 720. Если события из старого лога пропали, причина может быть в этом. Лечится командой `./siglens_up.sh reset` и повторной отправкой.
- Несколько событий в одном запросе отправляются как JSON-объекты через перевод строки. JSON-массив SigLens отклоняет.
- Событие становится доступно для поиска через несколько секунд после отправки. Запрос сразу после загрузки может вернуть ноль.
- На диске, заполненном больше чем на 95%, приём через `/elastic/_bulk` отклоняется с ошибкой `no storage available`.
- В SigLens нет авторизации. Поэтому порты по умолчанию открыты только на localhost. Если в логе есть пароли или персональные данные, наружу их лучше не открывать.
- Поля `timestamp` и `index` служебные. Колонки с такими именами в событие не попадут.

## Как добавить парсер для другого формата

Парсер и отправщик связаны только через CSV. Поэтому новый формат добавляется отдельным скриптом, который на выходе даёт такой же CSV, а отправщик остаётся прежним. Имя по образцу: `<формат>_to_csv.py`.

Что должен делать парсер:

- Писать CSV в UTF-8 с заголовком. Одна строка это одно событие.
- Оставлять колонку со временем в одном формате на весь файл. Её имя и формат потом передаются отправщику ключами `--time-column` и `--time-format`.
- Сохранять исходные поля как есть, а всё вычисленное добавлять новыми колонками. Так сделано с `AuthUser` и `AuthPass`: исходный заголовок остался, раскодированные значения лежат рядом.
- Приводить к одному виду значения, по которым потом будут группировать: логины, адреса, имена хостов.
- Пустое значение писать пустой строкой. Отправщик такие поля в событие не кладёт.
- Давать колонкам имена без пробелов и точек, иначе в запросах их придётся экранировать.
- Читать вход построчно и не держать весь файл в памяти.
- В конце печатать число записанных строк. Его удобно сверять с числом событий после загрузки.

Чего в парсере делать не надо: менять типы и пересчитывать время. CSV всё равно хранит текст, поэтому числа и время разбирает отправщик.

## Как добавить отправку в другую систему

Отправщик читает тот же CSV, поэтому для другой системы пишется новый скрипт `send_to_<система>.py`, а парсеры остаются прежними.

На что смотреть в первую очередь:

- Откуда система берёт время события. У SigLens это поле `timestamp` в миллисекундах. У других систем поле и единицы другие, и если ошибиться, события молча получат время загрузки.
- Куда попадают поля. Сначала стоит отправить одно событие и посмотреть, как оно выглядит в поиске, и только потом грузить всё.
- Как передаётся пачка: массивом, объектами через перевод строки или по одному.
- Есть ли срок хранения и не попадает ли под него старый лог.
- Сохраняются ли типы. Числа должны уходить числами, иначе сравнения и агрегаты не работают.

Что стоит повторить из `send_to_siglens.py`:

- проверку, что в индексе ещё нет событий за этот период;
- отправку пачками с повтором при ошибке;
- остановку на первой строке, где не разобралось время, вместо подстановки текущего;
- сверку количества событий после загрузки.
